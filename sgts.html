Qué es SGTS y qué problemas resuelve

El sistema representa un escenario habitual de software empresarial: usuarios que registran solicitudes, personal técnico que las atiende y responsables que necesitan controlar asignaciones, estados, prioridades y trazabilidad.

GESTIÓN

Tickets

Registro, consulta, edición y eliminación lógica de solicitudes de soporte, manteniendo información sobre categoría, prioridad, estado y usuario creador.

OPERACIÓN

Asignaciones

Los tickets pueden ser asignados a personal técnico, permitiendo separar la creación de una solicitud de su posterior atención.

TRAZABILIDAD

Historial

Los cambios relevantes del ticket pueden registrarse para conservar información sobre estados, prioridades y evolución de la atención.

ARCHIVOS

Adjuntos

Los tickets pueden asociarse con archivos físicos, almacenando en base de datos sus metadatos y utilizando nombres físicos independientes.

Arquitectura

Separación de responsabilidades

SGTS utiliza una arquitectura por capas. Cada proyecto tiene una responsabilidad definida y las dependencias permiten separar presentación, reglas de negocio, persistencia, infraestructura y modelos compartidos.

PRESENTACIÓN

SGTS.Web

Punto de entrada HTTP. Contiene Controllers, Razor Views, middleware, filtros, autenticación, autorización y recursos del frontend.

NEGOCIO

SGTS.Business

Contiene servicios, validadores, reglas de negocio, autorización contextual, mapeos y coordinación de casos de uso.

PERSISTENCIA

SGTS.Persistence

Implementa AppDbContext, entidades, configuraciones IEntityTypeConfiguration, repositorios y migraciones utilizando Entity Framework Core y SQL Server.

INFRAESTRUCTURA

SGTS.Infrastructure

Encapsula servicios técnicos como JWT, hashing y verificación de contraseñas y almacenamiento físico de archivos.

MODELOS

SGTS.Models

Contiene DTOs de entrada y salida, modelos de paginación, solicitudes de ordenamiento, enums y modelos relacionados con archivos.

COMPARTIDO

SGTS.Shared

Reúne enums, excepciones, códigos de error y utilidades compartidas entre las diferentes capas.

DATABASE

SQL Server

Persistencia relacional de usuarios, tickets, asignaciones, comentarios, adjuntos, categorías, prioridades, estados e historial.

Flujo técnico

Qué sucede cuando se procesa una solicitud

La separación por capas también permite visualizar el recorrido de una operación desde la entrada HTTP hasta la persistencia.

01

Request

El cliente realiza una solicitud HTTP hacia el Controller correspondiente.

02

Service

El servicio coordina la operación y aplica las reglas correspondientes al caso de uso.

03

Repository

El repositorio abstrae las operaciones de persistencia y trabaja con Entity Framework Core.

04

Database

Entity Framework Core traduce las operaciones y SQL Server mantiene los datos persistentes.

Principio aplicado

El Controller no concentra la lógica de negocio ni las consultas a la base de datos. Su responsabilidad principal es manejar la comunicación HTTP y delegar la operación a la capa correspondiente.

Patrones

Cómo está organizado el código

Los patrones utilizados buscan resolver problemas concretos dentro del sistema: separación de responsabilidades, reutilización, acceso a datos, transformación de modelos y composición de servicios.

DATA ACCESS

Repository Pattern

Encapsula el acceso a los datos y evita que los servicios tengan que conocer directamente los detalles de las consultas realizadas mediante Entity Framework Core.

ITicketRepository
BUSINESS

Service Layer

Los servicios representan operaciones de aplicación y coordinan validación, reglas, repositorios, mapeos y respuestas.

TicketService
DATA TRANSFER

DTO Pattern

Se utilizan modelos específicos para las entradas y salidas de las operaciones, evitando exponer directamente las entidades de persistencia.

TicketCreateDto
DEPENDENCIES

Dependency Injection

Los servicios, repositorios y componentes técnicos se registran mediante el contenedor de dependencias de ASP.NET Core.

IServiceCollection
MAPPING

Data Mapper

Se separan las entidades de persistencia de los modelos que consume la aplicación mediante transformaciones explícitas o AutoMapper.

Entity → DTO
CONTROL

Guard / EnsureFound

Se utilizan mecanismos reutilizables para validar precondiciones y evitar repetir comprobaciones de entidades inexistentes.

EnsureFound()

Seguridad

Autenticación y autorización

La seguridad se aborda en diferentes niveles. El sistema separa la autenticación del usuario de las reglas que determinan qué operaciones puede realizar.

AUTENTICACIÓN

Cookie + JWT Bearer

La aplicación utiliza Cookie Authentication para el flujo MVC y JWT Bearer para las operaciones expuestas mediante API.

  • Cookie Authentication
  • JWT Bearer
  • Validación de firma
  • Issuer y Audience
  • Validación de lifetime
  • ClockSkew configurado en cero
AUTORIZACIÓN

Claims, roles y policies

La autorización utiliza información del usuario autenticado para determinar el acceso a funcionalidades y operaciones específicas.

  • Claims de usuario
  • Roles
  • Authorization Policies
  • PersonalTecnico
  • SoloSupervisor
  • SoloAdministrador
CONTEXTO

CurrentUser

El acceso a la identidad autenticada se abstrae mediante un servicio de usuario actual. De esta forma, las capas que necesitan conocer al usuario no dependen directamente del frontend para recibir su identificador.

IdUsuario RolUsuario
NEGOCIO

Autorización contextual

Las policies no reemplazan las reglas de negocio. Las operaciones también pueden verificar si el usuario autenticado está autorizado para realizar una acción sobre un recurso concreto.

TicketBusinessValidator
